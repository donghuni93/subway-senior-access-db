## p.13

장점                                                        데이터베이스 관리 시스템의 장·단점

■ 데이터 중복을 통제할 수 있다.
 ▪ 데이터베이스에 데이터를 통합하여 관리하므로 데이터 중복 문제 해결

■ 데이터 독립성이 확보된다.
 ▪ 응용 프로그램 대신 데이터베이스에 접근하고 관리하는 모든 책임 담당
  → 응용 프로그램과 데이터베이스 사이에 독립성이 확보됨

■ 데이터를 동시 공유할 수 있다.
 ▪ 동일한 데이터를 여러 응용 프로그램이 공유하여 동시 접근할 수 있게 지원
  → 동시 접근 제어 기술 보유

■ 데이터 보안이 향상된다.
 ▪ 중앙 집중식으로 데이터를 관리하므로 효율적인 접근 제어 가능
  • 권한이 없는 사용자의 접근, 허용되지 않은 데이터와 연산에 대한 요청 차단

## p.18

Recent Update

교수님, 데이터베이스의 역사를 거슬러 올라가면 가장 뿌리에 있는 **계층형 데이터베이스(Hierarchical Database Management System, HDBMS)**를 만나게 됩니다. 1960년대 IBM의 IMS(Information Management System)가 대표적이며, 현대의 RDBMS나 NoSQL을 이해하는 데 있어 '부모-자식' 관계의 기틀을 마련한 모델입니다.

공학적 엄밀성을 갖추어 상세히 요약해 드립니다.

🌲 계층형 데이터베이스(HDBMS)의 정의
데이터를 트리(Tree) 구조로 구성하여 집단 간의 상위-하위 관계를 나타내는 모델입니다. 하나의 부모(Parent) 레코드는 여러 개의 자식(Child) 레코드를 가질 수 있지만, 자식은 반드시 하나의 부모만을 가져야 하는 1:N 관계가 핵심입니다.

1. 주요 특징 (Engineering Characteristics)
• 구조적 단순성: 데이터 관계가 물리적으로 연결되어 있어 직관적이며, 위에서 아래로 흐르는 하향식(Top-down) 구조를 가집니다.
• 참조 무결성 자동 보장: 부모 레코드가 삭제되면 연결된 자식 레코드도 함께 처리되어야 하므로 계층 간의 종속성이 매우 강합니다.
• 포인터(Pointer) 기반 접근: 인덱스(Index) 기반인 현대 DB와 달리, 물리적인 주소값(Pointer)을 따라 이동하므로 단순 조회 속도는 매우 빠릅니다.

2. 장단점 분석 (Pros and Cons)
구분 | 내용
장점 | 1. 고속 처리: 관계가 고정되어 있어 단순 반복 검색 시 오버헤드가 적음.
 | 2. 데이터 일관성: 명확한 계층 구조 덕분에 중복 데이터 제어가 용이함.
단점 | 1. 유연성 부족: 구조 변경(스키마 변경)이 매우 어려움.
 | 2. 다대다(N:M) 표현 불가: 자식이 여러 부모를 가질 수 없어 구조적 한계 존재.
 | 3. 복잡한 경로: 데이터를 찾기 위해 반드시 루트(Root)부터 경로를 따라 내려가야 함.

## p.19

Recent Update

교수님, 계층형 DB의 가장 큰 약점이었던 **"다대다(N:M) 관계 표현의 불가능"**을 해결하기 위해 등장한 **네트워크 데이터베이스(Network Database Management System, NDBMS)**를 상세히 요약해 드립니다.

1970년대 초반 CODASYL(데이터 시스템 언어 컨퍼런스) 그룹에 의해 표준화되었으며, 데이터 간의 복잡한 연결성을 그물망(Mesh) 형태로 설계한 모델입니다.

❄ 네트워크 데이터베이스(NDMS)의 정의
데이터를 그래프(Graph) 구조로 구성하여, 하나의 자식 레코드가 여러 개의 부모 레코드를 가질 수 있도록 허용한 모델입니다. 계층형의 'Tree' 구조를 넘어선 'Mesh' 구조라고 이해하시면 공학적으로 정확합니다.

1. 주요 특징 (Engineering Characteristics)
• 다대다(N:M) 관계 지원: 소유자(Owner)와 구성원(Member)이라는 개념을 도입하여, 한 구성원이 여러 소유자에게 속할 수 있습니다.
• 세트(Set) 구조: 데이터 간의 관계를 'Set'이라는 단위로 정의하며, 물리적 포인터를 사용하여 레코드 사이를 직접 연결합니다.
• 복잡한 포인터 체계: 데이터 간의 연결이 매우 긴밀하여, 특정 데이터를 찾기 위해 다양한 경로(Navigation)를 선택할 수 있습니다.

2. 장단점 분석 (Pros and Cons)
구분 | 내용
장점 | 1. 유연한 관계 표현: 계층형에서 불가능했던 복잡한 현실 세계의 관계를 반영 가능.
 | 2. 접근 효율성: 데이터 간 직접 연결로 인해 특정 경로 탐색 속도가 매우 빠름.
 | 3. 데이터 중복 최소화: 다중 부모를 허용하므로 동일 데이터를 여러 곳에 복제할 필요가 없음.
단점 | 1. 설계의 복잡성: 포인터 구조가 너무 복잡해지면 '데이터 스파게티'가 발생하여 유지보수가 불가능해짐.
 | 2. 종속성: 데이터 구조를 변경하려면 관련된 모든 포인터를 수정해야 함.
 | 3. 전문 지식 요구: 사용자가 데이터의 물리적 저장 구조(경로)를 완벽히 이해해야 쿼리가 가능함.

## p.23

Recent Update

교수님, 90년대 데이터베이스 학계와 산업계의 최대 화두였던 **객체 지향 데이터베이스(Object-Oriented Database, OODB)**가 왜 시장의 주류가 되지 못하고 '화려한 실패'로 끝났는지, 그 공학적·비즈니스적 사유를 날카롭게 분석해 드립니다.

당시에는 C++, Java 등 객체 지향 언어가 급부상하면서 "데이터도 객체 형태로 저장하는 것이 자연스럽다(Seamless)"는 논리가 지배적이었지만, 현실의 벽은 높았습니다.

✎ OODB가 시장에서 도태된 5가지 핵심 이유

1. RDBMS의 'SQL'이라는 거대한 표준 (Standardization)
RDBMS에는 SQL이라는 강력하고 단순한 공통 언어가 있었습니다.
• OODB의 문제: 제품마다 쿼리 방식과 인터페이스가 제각각이었습니다. 개발자들은 특정 OODB 제품에 종속되는(Vendor Lock-in) 것을 꺼려했습니다.
• RDBMS의 반격: SQL이 표준화되면서 "사람은 바뀌어도 데이터는 남는다"는 기업의 철학에 부합했습니다.

2. '임계 질량'을 넘지 못한 생태계 (Ecosystem)
• 도구의 부재: RDBMS는 리포팅 툴, 데이터 시각화, 백업 솔루션 등 주변 생태계가 어마어마했습니다.
• 데이터의 고립: OODB에 저장된 데이터는 해당 객체를 정의한 프로그래밍 언어가 없으면 해석하기 어려웠습니다. 즉, 데이터의 독립성(Data Independence) 확보에 실패했습니다.

3. 객체-관계 임피던스 불일치(Impedance Mismatch)의 역설
OODB는 이 불일치를 해결하려 등장했지만, 정작 시장은 **ORM(Object-Relational Mapping)**이라는 타협점을 찾아냈습니다.
• 해결책의 등장: Hibernate, JPA 같은 기술이 나오면서 "DB는 안정적인 RDBMS를 쓰고, 코드단에서만 객체로 다루자"는 방식이 정착되었습니다. 굳이 DB 엔진 자체를 바꿀 모험을 할 필요가 없어진 것입니다.

4. 선언적(Declarative) 쿼리의 부재
• RDBMS: "무엇(What)을 가져와라"라고 명령하면 최적화기(Optimizer)가 알아서 찾아옵니다.
• OODB: "어떻게(How) 포인터를 따라가라"는 식의 절차적 접근이 많았습니다. 이는 데이터 양이 많아질수록 쿼리 작성과 최적화를 어렵게 만들었습니다.

5. 관계 모델(Relational Model)의 수학적 견고함
Codd 박사가 정립한 관계 모델은 집합론이라는 탄탄한 수학적 기초 위에 있습니다.
• OODB: 공학적으로는 유연해 보였지만, 수학적인 엄밀함과 데이터 무결성을 증명하는 데 있어 관계 모델만큼의 신뢰를 주지 못했습니다.

4세대: NoSQL·NewSQL DBMS

■ NoSQL DBMS : 비정형 데이터를 처리하는데 적합하고 확장성이 뛰어남

1. MongoDB (CP 방향): 일관성을 중시합니다. 데이터 복제 중 오류가 나면 일시적으로 쓰기를 중단하더라도 데이터의 정확성을 지키려 노력합니다.
2. Cassandra (AP 방향): 가용성을 최우선으로 합니다. 서버 몇 대가 죽어도 시스템은 중단 없이 돌아가야 하는 대규모 분산 환경에 최적화되어 있습니다.
3. Redis (Performance): '성능' 그 자체에 올인합니다. 하드디스크가 아닌 RAM에 데이터를 저장하므로, 휘발성 데이터나 초고속 처리가 필요한 곳에 필수적입니다.
