## p.7

요구 사항 분석

■ 설계 1 단계 : 요구 사항 분석
 ▪ 목적
   • 사용자의 요구 사항을 수집하고 분석하여 개발할 데이터베이스의 용도 파악
     – 업무에 필요한 데이터가 무엇인지, 그 데이터에 어떤 처리가 필요한지 등을 고려
 ▪ 결과물
   • 요구 사항 명세서
 ▪ 주요 작업
   • 데이터베이스를 실제로 사용할 주요 사용자의 범위 결정
   • 사용자가 조직에서 수행하는 업무 분석
   • 면담, 설문 조사, 업무 관련 문서 분석 등의 방법을 이용해 요구 사항 수집
   • 수집된 요구 사항에 대한 분석 결과를 요구 사항 명세서로 작성

## p.8

요구 사항 분석

■ 요구 사항 분석 예 : [한빛 마트 데이터베이스]
 ▪ 인터넷으로 회원에게 상품을 판매하는 한빛 마트의 데이터베이스 개발

[그림 8-4 한빛 마트의 데이터베이스를 위한 요구 사항 명세서]
1. 한빛 마트에 회원으로 가입하려면 회원아이디, 비밀번호, 이름, 나이, 직업을 입력해야 한다.
2. 가입한 회원에게는 등급과 적립금이 부여된다.
3. 회원은 회원아이디로 식별한다.
4. 상품에 대한 상품번호, 상품명, 재고량, 단가 정보를 유지해야 한다.
5. 상품은 상품번호로 식별한다.
6. 회원은 여러 상품을 주문할 수 있고, 하나의 상품을 여러 회원이 주문할 수 있다.
7. 회원이 상품을 주문하면 주문에 대한 주문번호, 주문수량, 배송지, 주문일자 정보를 유지해야 한다.
8. 각 상품은 한 제조업체가 공급하고, 제조업체 하나는 여러 상품을 공급할 수 있다.
9. 제조업체가 상품을 공급하면 공급일자와 공급량 정보를 유지해야 한다.
10. 제조업체에 대한 제조업체명, 전화번호, 위치, 담당자 정보를 유지해야 한다.
11. 제조업체는 제조업체명으로 식별한다.
12. 회원은 게시글을 여러 개 작성할 수 있고, 게시글 하나는 한 명의 회원만 작성할 수 있다.
13. 게시글에 대한 글번호, 글제목, 글내용, 작성일자 정보를 유지해야 한다.
14. 게시글은 글번호로 식별한다.

## p.9

요구공학(Requirement Engineering)

[다이어그램: 요구공학(Requirement Engineering) 계층도. 최상위 "요구공학(Requirement Engineering)" 아래 두 갈래.
- 왼쪽 "요구사항 개발(Requirement Development)" — 주석: "기능 요구사항과 비즈니스 목표를 달성할 수 있는 제품특성을 식별하는 과정". 하위 4개: 요구사항 도출, 요구사항 분석, 요구사항 명세화, 요구사항 검증. 하위 항목 사이 화살표 라벨: 명확화, 재작성, 재평가, 수정 및 차이 해소.
- 오른쪽 "요구사항 관리(Requirement Management)" — 주석: "고객과 요구사항에 대해 합의하고 이를 유지하며 관리하는 활동". 하위 4개: 요구사항 협상, 요구사항 베이스라인, 요구사항 변경관리, 요구사항 확인수행.]

[삽입 상자: 요구사항 도출]
- 정의
  > 고객을 이해하고 그들이 무엇을 필요로 하는지 찾아내는 활동
  > 고객으로부터 제시되는 추상적 요구에 대해 관련 정보를 식별하고 수집해 구체적인 요구사항으로 표현하는 활동
- 요구사항 도출을 위한 주요기법
  인터뷰 - 가장 전통적인 방식으로, 분석가와 고객간 인터뷰 내용을 바탕으로 도출
  시나리오 - Use Case가 대표적인 기법이며, 요구사항에 대한 스토리 작성
  프로토타입 - 프로토타입(Prototype)을 생성해 고객의 피드백(Feedback)으로 요구사항 도출
  기존 요구사항 관련 문서 파악 - 현행 업무 및 현행 시스템 이용현황을 관찰 및 분석
  기타 기법 - 벤치마킹(Benchmarking), 브레인스토밍(Brain Storming), 역할극(Role Play)등 다양한 기법 활용

물리적 설계(1/3)

(우측 상단 라벨: Recent Update)

[삽입 상자 1: 요약]
질의 응답시간을 줄이는 것은 물리적 설계의 가장 핵심적인 목적(1순위)이 맞으며, 이를 달성하기 위한 구체적 수단이 **인덱스·반정규화·파티셔닝**이고, 부수적으로 **저장 공간 효율화**와 **백업/보안/동시성 설계**가 함께 이루어집니다.

[삽입 상자 2: 논리적 설계와 물리적 설계 비교표]

| 구분 | 논리적 설계 (Logical Design) | 물리적 설계 (Physical Design) |
|---|---|---|
| 핵심 주안점 | 데이터 정합성, 무결성, 중복 제거 | 질의 응답시간 단축(성능), 저장 공간 효율 |
| DBMS 종속성 | 특정 DBMS에 독립적 (추상적 스키마) | 특정 DBMS(Oracle, MySQL, PostgreSQL 등)에 종속적 |
| 주요 작업 | ERD 변환, 정규화(1NF~BCNF), 키·제약조건 정의 | 인덱스 설계, 반정규화, 파티셔닝, 저장 구조·데이터 타입 확정 |

[삽입 상자 3]
데이터베이스 물리적 설계의 3대 핵심 주안점
1. **성능 최적화 — 질의 응답시간(Response Time) 및 처리량(Throughput)**
   - 사용자가 쿼리를 날렸을 때 결과가 돌아오는 시간(응답시간)을 줄이고, 단위 시간당 처리하는 트랜잭션 수(처리량)을 극대화하는 것이 최대 목표입니다.
   - 이를 위해 **인덱스(Index) 설계, 반정규화(Denormalization), 파티셔닝(Partitioning)**, 클러스터링(Clustering) 기법을 적용합니다.
2. **저장 공간 효율성 (Storage Utilization)**
   - 데이터 타입과 길이를 최적화(예: 불필요한 `VARCHAR` 크기 축소)하고 압축 기법을 적용하여 디스크 공간 낭비와 메모리 I/O 비용을 줄입니다.
3. **데이터 보안 및 장애 복구·동시성 제어 (운영 안정성)**
   - 사용자별 접근 권한(뷰·권한 부여), 백업 및 복구 주기 설계, 대용량 트랜잭션 환경에서의 락(Lock) 경합 최소화 등 실제 운영 환경의 안정성을 확보합니다.

## p.69

물리적 설계(2/3)

(우측 상단 라벨: Recent Update)

[삽입 상자 1]
물리적 스키마(Physical Schema)란 데이터베이스에 저장된 데이터가 **실제 하드디스크나 SSD 같은 물리적 저장 장치에 어떤 파일 구조, 인덱스, 블록 단위로 기록되고 접근되는지를 정의한 설계도**입니다.

우리가 흔히 보는 엑셀 표 형태의 테이블 구조(논리적 스키마)가 아니라, 그 테이블이 디스크 내부에서 **0과 1의 바이트(Byte) 배열로 어떻게 쪼개지고 정렬되어 저장되는지**를 다룹니다.

[삽입 상자 2]
물리적 스키마는 DBMS(Oracle, MySQL, PostgreSQL 등)의 내부 저장 엔진에 종속적이며, 주로 다음 4가지를 결정합니다.
- **레코드 및 데이터 타입의 실제 저장 크기:** 문자열(`VARCHAR(50)`)이 실제로 몇 바이트를 차지하는지, 숫자(`INT`, `BIGINT`)가 어떻게 인코딩되는지, NULL 값을 어떻게 표시하는지 정의합니다.
- **인덱스(Index) 구조:** 검색 속도를 높이기 위해 B+Tree나 Hash 구조의 인덱스를 어떤 컬럼에, 어떤 방식으로 생성하여 디스크에 저장할지 결정합니다.
- **파일 편성 및 블록(Page) 할당 방식:** 데이터를 힙(Heap) 파일, 순차 파일, 해시 파일 중 어떤 형태로 저장할지, 디스크 블록(예: 8KB, 16KB 페이지) 단위로 어떻게 묶어 읽을지 정의합니다.
- **파티셔닝(Partitioning) 및 테이블스페이스(Tablespace):** 대용량 테이블을 날짜나 지역 기준으로 여러 물리적 파일/디스크에 나누어 저장하는 경로와 규칙을 지정합니다.

[삽입 상자 3] (번호 또는 불릿 기호가 잘려 보임: ". 물리적 스키마의 핵심 가치")
. 물리적 스키마의 핵심 가치: **"물리적 데이터 독립성"**

물리적 스키마가 개념 스키마와 분리되어 있기 때문에, DBA가 검색 속도를 높이기 위해 **인덱스를 새로 추가하거나 SSD 저장 경로를 바꾸고 파티션을 쪼개더라도(물리적 스키마 변경), 상위 애플리케이션의 SQL 쿼리나 테이블 구조(개념·외부 스키마)는 전혀 수정할 필요가 없습니다.** 이를 데이터베이스의 물리적 데이터 독립성(Physical Data Independence)이라고 합니다.

물리적 설계(3/3)

(우측 상단 라벨: Recent Update)

[삽입 상자 1: 요약]
일반적인 웹·앱 서비스 기준에서 **DB 순수 질의응답시간은 10ms~100ms 이내**가 표준이며, **100ms(0.1초)를 넘어가기 시작하면** 인덱스 추가나 쿼리 튜닝(슬로우 쿼리 개선) 대상으로 봅니다.

[삽입 상자 2]
실무에서 응답시간을 판단하는 3가지 핵심 기준
- ① UX(사용자 경험)의 심리적 마지노선 (닐슨의 3단계 법칙):
  - **0.1초 (100ms):** 사용자가 지연 없이 즉각 반응한다고 느끼는 한계 (DB 쿼리는 보통 이 안에 끝나야 앱 전체가 쾌적합니다).
  - **1.0초 (1,000ms):** 사고의 흐름이 끊기지 않는 한계. 이 시간을 넘기면 로딩 표시(Spinner)가 필요합니다.
  - **10초:** 사용자가 화면을 이탈하는 한계.
- ② 평균(Average)이 아닌 백분위수(P95, P99) 기준 관리:
  - 실무 물리적 설계에서는 "평균 50ms"보다 "전체 질의의 99%(P99)가 100ms 이내에 응답할 것"처럼 꼬리 지연(Tail Latency)을 기준으로 튜닝합니다. (일부 악성 쿼리가 DB 락을 잡으면 평균은 좋아 보여도 실제 서비스는 먹통이 되기 때문입니다.)
- ③ 단순 DB 실행 시간 vs 전체 네트워크 왕복 시간:
  - DB 내부 쿼리 실행 시간(DB Time)이 5ms~30ms 수준이어야, 애플리케이션 로직과 네트워크 통신 시간을 합쳤을 때 최종 사용자 화면에 200ms 이내로 표시할 수 있습니다.

[삽입 상자 3: 응답 분야별 응답시간 목표 표]

| 응답 분야 (시스템 유형) | 통상 응답시간 목표 | 사용자 체감 및 특징 | 주요 사용 DB / 기술 |
|---|---|---|---|
| 초저지연 실시간 처리 (금융 HFT, 게임 매칭, 광고 입찰 RTB, 캐시 조회) | 1ms ~ 10ms 이하 | 시스템 간 즉각 반응 필수. 10ms만 넘어도 기회비용 손실이나 게임 렉 발생 | Redis, Memcached (인메모리 DB) |
| 일반 웹 / 모바일 앱 (OLTP) (쇼핑몰 상품 조회, 로그인, 송금, SNS 피드) | 10ms ~ 100ms 이내 (전체 API 기준 200ms~500ms 이하) | 100ms 이하여야 사용자가 "즉시 반응한다"고 느낌 (UX 황금 기준) | MySQL, PostgreSQL, Oracle (인덱스 최적화 필수) |
| 사내 업무 시스템 (ERP / CRM) (인사·회계 조회, 병원 EMR 진료 차트) | 100ms ~ 1초 이내 | 수십 개 테이블이 조인되는 복잡한 조건 검색이 많아 1초 이내면 양호 | RDBMS (Oracle, MS-SQL 등) |

## p.76

트랜잭션의 개념

■ 하나의 작업을 수행하는데 필요한 데이터베이스 연산들을 모아놓은 것

■ 작업 수행에 필요한 SQL 문들의 모임
 ▪ 특히, 데이터베이스를 변경하는 INSERT, DELETE, UPDATE 문의 실행을 관리

■ 논리적인 작업의 단위

■ 장애 발생 시 복구 작업이나 병행 제어 작업을 위한 중요한 단위로 사용됨

■ 데이터베이스의 무결성과 일관성을 보장하기 위해 작업 수행에 필요한 연산들을 하나의 트랜잭션으로 제대로 정의하고 관리해야 함

## p.77

트랜잭션의 예

■ 트랜잭션의 예 : 계좌이체

[다이어그램: 계좌이체 전의 데이터베이스 상태(원통: 성호 잔액 : 10,000원 / 은경 잔액 : 0원) → "계좌이체 트랜잭션" 상자 → 계좌이체 후의 데이터베이스 상태(원통: 성호 잔액 : 5,000원 / 은경 잔액 : 5,000원)]
계좌이체 트랜잭션:
1. 성호 계좌에서 5,000원 인출
```sql
UPDATE 계좌
SET    잔액 = 잔액 - 5000
WHERE  계좌번호 = 100;
```
2. 은경 계좌에 5,000원 입금
```sql
UPDATE 계좌
SET    잔액 = 잔액 + 5000
WHERE  계좌번호 = 200;
```
[말풍선] 처리 순서는 중요하지 않지만 두 개의 UPDATE 문이 모두 정상적으로 실행되어야 함

## p.78

트랜잭션의 특성

■ 트랜잭션의 특성 (ACID 특성)

[다이어그램: 최상위 "트랜잭션의 특성" 아래 4개 하위 상자: 원자성, 일관성, 격리성, 지속성]

■ 특성: 원자성 (Atomicity)
 ▪ 트랜잭션의 연산들이 모두 정상적으로 실행되거나 하나도 실행되지 않아야 하는 All-or-nothing 방식을 의미
 ▪ 만약 트랜잭션 수행 도중 장애가 발생하면?
   • 지금까지 실행한 연산 처리를 모두 취소하고, 데이터베이스를 트랜잭션 작업 전 상태로 되돌려야 함
 ▪ 원자성의 보장을 위해 장애 발생 시 회복 기능이 필요

| 트랜잭션의 특성 | DBMS의 기능 |
