# 요구사항 명세서 (2026-11-17, 실제 데이터 반영)

교재 8·9장 설계 절차의 첫 단계인 요구사항 분석 결과이다. 제안서(11/3) 1.3절의 사용자 정의와 2.1.2절 (1)의 요구 사항 명세 초안 ①~⑨를, 실제 API 응답과 파일을 확인한 결과에 맞추어 다시 작성하였다. 이 문서의 수치는 `subway_access_db`(MySQL 8.0.46)와 `data/raw/`의 원천 파일을 2026-11-17에 직접 조회한 값이다.

- 기준 스키마: `sql/01_schema.sql`
- 정제 규칙 구현: `src/preprocess.py`, 적재 구현: `src/load_db.py`, 수집 구현: `src/collect.py`
- 관련 문서: 개념적 설계 `02_ER다이어그램.md`, 논리적 설계 `03_릴레이션스키마.md`, 정규화 `04_정규화.md`, 물리적 설계 `05_물리스키마.md`

## 1. 개요

### 1.1 목적과 범위

본 시스템은 서울교통공사 1~8호선 역의 고령 이용 수요와 승강기(엘리베이터·에스컬레이터) 운영 정보를 하나의 관계형 데이터베이스로 통합하고, 매시 수집한 승강기 상태를 비가동 이력으로 축적한다. 이 데이터베이스로 다음 세 질문에 답한다.

| 번호 | 질문 |
|---|---|
| 질문 1 | 고령 이용 수요는 어느 역, 어느 시간대에 집중되는가? |
| 질문 2 | 승강기 비가동은 어느 역에서 얼마나 자주, 얼마나 오래 일어나며, 그때 영향을 받을 수 있는 고령 이용객은 몇 명으로 추정되는가? |
| 질문 3 | 고령 수요, 수직 이동 부담, 승강기 운영 상태를 함께 보면 역은 어떤 유형으로 나뉘며, 우선 관리할 역은 어디인가? |

| 항목 | 내용 |
|---|---|
| 대상 역 | 2025년 노인 승하차 자료(OA-22483)에 나오는 1~8호선 역번호 278개. 이 가운데 전체 승하차 파일에도 있는 역은 273개이다. |
| 대상 시설 | 엘리베이터(EV) 866대, 에스컬레이터(ES) 1,884대. 휠체어리프트 41대와 무빙워크 18대는 제외한다. |
| 이용 수요 기간 | 2025.1.1~2025.12.31 (365일, 시간대 20개) |
| 운영 상태 기간 | 2026.11.17 00:56 첫 수집부터 매시. 작업 스케줄러 등록 기간은 12.9 00시까지이다. |
| 제외 | 9호선·코레일 등 다른 운영기관 구간, 시점별 이용객 예측, 1시간 미만의 짧은 비가동 |

### 1.2 분석 단위: 역(호선별)과 역사(驛舍)

제안서는 "역은 호선별로 구분하며, 환승역은 호선마다 별도의 역으로 본다"고 정하였다. 데이터를 적재한 결과 환승역에서는 승하차와 승강기가 한 호선의 역번호로만 기록되는 경우가 있었다.

| 역사 | 호선별 역 | 2025년 승하차 기록 | 승강기 수 |
|---|---|---|---|
| 충무로 | 3호선 321 | 20일, 노인 승차 합계 0, 전체 승하차 파일에는 없음 | 0대 |
| | 4호선 423 | 365일, 전체 승차 10,822,161명, 노인 승차 1,221,637명 | 27대 |
| 청구 | 5호선 2538 | 365일 | 0대 |
| | 6호선 2635 | 365일 | 15대 |
| 연신내 | 3호선 311 | 365일 | 5대 |
| | 6호선 2615 | 23일, 노인 승차 합계 0, 전체 승하차 파일에는 없음 | 8대 |

호선별 역 단위로 집계하면 3호선 충무로는 이용객 0명·승강기 0대로 나타나 실제와 다르다. 따라서 데이터는 호선별 역(STATION) 단위로 저장하되, 같은 건물을 쓰는 호선별 역을 역사(STATION_COMPLEX)로 묶고 질문 1~3의 분석과 대시보드 표시는 역사 단위로 한다. 278개 역은 242개 역사로 묶이며, 둘 이상의 호선이 있는 역사는 34개(2개 호선 32개, 3개 호선 2개: 종로3가·동대문역사문화공원)이다.

### 3.2 역 식별 요구

원천마다 역을 가리키는 값이 다르다. 모든 자료를 역번호(station_no)로 통일한다.

| 체계 | 예 (서울역 1호선 / 용답 / 방화) | 쓰는 자료 |
|---|---|---|
| 역코드 STN_CD (4자리 문자) | 0150 / 0244 / 2511 | D-1, D-8, D-9 |
| 승하차 역번호 | 150 / 244 / 2511 | D-6, D-7 |
| 외부코드 FR_CODE | 133 / 211-1 / 510 | D-1 |
| 역명만 | 서울 / 용답 / 방화 | D-2, D-3, D-4, D-5, D-10 |

| ID | 요구 |
|---|---|
| D-R1 | 역번호는 승하차 자료의 역번호를 쓰며, 이는 역코드(STN_CD)를 정수로 쓴 값과 같다(0150 → 150). 처음에 외부코드를 역번호로 보고 연결하였을 때 278개 중 113개만 연결되었고, 역코드 정수로 바꾼 뒤 278개 모두 연결되었다. |
| D-R2 | 외부코드는 역을 식별하는 또 다른 값으로 저장하고 중복을 허용하지 않는다. 노선별 역 정보에 없는 7호선 까치울(2753)·상동(2758)은 외부코드가 비어 있다. |
| D-R3 | 역명으로만 주어지는 자료는 (호선, 정규화한 역명)으로 역을 찾는다. 정규화는 괄호와 괄호 안 글자 제거, 공백 제거, 끝의 '역' 제거이다("서울역(1)" → "서울"). |
| D-R4 | 이름이 바뀐 역과 원천의 줄임 표기는 호선별 별칭표로 맞춘다. 역명 변경 5건(4호선 당고개→불암산, 7호선 뚝섬유원지→자양, 7호선 총신대입구→이수, 4호선 미아삼거리→미아사거리, 5호선 동대문운동장→동대문역사문화공원), 역사심도 파일 표기 9건(을지3가→을지로3가, 애오게→애오개, DMC→디지털미디어시티 등). |
| D-R5 | 출입구 폐쇄 자료처럼 역명이 잘려 오는 경우("건대입구(")는 같은 호선에서 정규화 역명의 앞부분이 하나의 역과만 일치할 때 그 역으로 본다. |
| D-R6 | 연결하지 못한 원천 행은 버리지 않고 `data/clean/unmatched.csv`에 출처·값·사유를 남긴다. 현재 3건(외부코드 없음 2건, 2호선 까치산 좌표 1건)이다. |

### 4.1 비가동 구간 계산 규칙

승강기 가동현황 API는 조회 시점의 상태만 준다. 시각별 스냅샷을 시간순으로 비교하여 구간을 만든다.

1. 비가동은 운행상태 `USE_YN`이 '사용가능'이 아닌 상태이다. 11/17 00:56 첫 수집에서 관측된 값은 '사용가능' 2,733대, '보수중' 76대이다.
2. 승강기가 비가동으로 처음 관측된 수집 시각을 시작 시각으로, 다시 사용가능으로 관측된 수집 시각을 종료 시각으로 한다. 복구 전에는 종료 시각을 비워 둔다.
3. 승강기마다 구간에 1부터 순번을 붙인다. 한 승강기에 진행 중인 구간은 하나뿐이다.
4. 어떤 수집에서 승강기가 응답에서 빠지면 상태를 모르는 것으로 보고 구간을 바꾸지 않는다.
5. 첫 수집 때 이미 비가동이던 승강기는 실제 시작 시각을 알 수 없으므로 첫 수집 시각을 시작 시각으로 기록한다. 00:56 첫 수집에서 보수중이던 76대 중 휠체어리프트 1대를 뺀 75건(ES 69, EV 6)이 이 경우이다. 01:42 수집에서 1건이 새로 시작되어 OUTAGE는 76건이 되었다.
6. '보수중'이 고장인지 계획 점검인지는 API로 구분할 수 없다. 1시간 안에 끝난 비가동은 관측되지 않을 수 있다.
7. 수집이 빠진 시각(PC 꺼짐 등)을 비가동 시간 산정에서 어떻게 처리할지는 정하지 않았다. 빠진 구간은 LOAD_LOG의 수집 간격으로 찾는다(`sql/02_checks.sql` 6번). [확인 필요: 결측 구간 처리 규칙]

## 6. 개체 명세

제안서 2.1.2절 (1)의 명세 ①~⑨를 실제 데이터 기준으로 다시 쓴 것이다. 괄호 안 수치는 2026-11-17 적재 결과이다.

① 노선은 노선번호로 식별하며 노선명을 가진다. 노선번호는 1~8이다. (8개)

② 역사는 역사번호로 식별하며 역사명을 가진다. 역사번호는 그 역사에 속한 역번호 가운데 가장 작은 값이다. 역사는 같은 건물을 쓰는 호선별 역의 묶음이며, 한 역사에는 하나 이상의 역이 있다. (242개, 이 중 둘 이상의 호선이 있는 역사 34개)

③ 역은 역번호로 식별하며 외부코드, 역명, 위도·경도, 승강장 형식, 층수, 준공연도, 정거장 깊이를 가진다. 역번호는 역코드(STN_CD)를 정수로 쓴 값이다. 외부코드는 역마다 다르지만 없는 역이 있다. 정거장 깊이가 음수이면 지상보다 높은 고가역이다. 역은 반드시 하나의 노선과 하나의 역사에 속하고, 한 노선에는 여러 역이 있다. 환승역은 호선마다 별도의 역이다. (278개, 외부코드 없음 2개, 정거장 깊이 없음 2개, 고가역 24개)

④ 환승은 역과 환승 노선명으로 구분하며 환승 거리와 소요 시간을 가진다. 환승 노선에는 공항철도·경의중앙선처럼 범위 밖 노선이 있으므로 상대 역이 아닌 노선명으로 기록한다. 환승은 역 없이 존재할 수 없다. (140건, 이 중 범위 밖 노선 54건)

⑤ 승강기는 승강기번호로 식별하며 종류(엘리베이터·에스컬레이터), 승강기명, 설치 위치, 운행 구간, 시설번호를 가진다. 같은 역 안에서 승강기명은 중복되지 않으며, 시설번호는 엘리베이터에만 있다. 승강기는 반드시 하나의 역에 설치되며, 승강기가 없는 역도 있다. (2,750대, 승강기가 없는 역 4개: 321, 2538, 2753, 2758)

⑥ 승강기 비가동 이력은 승강기별 순번으로 구분하며 상태, 시작 시각, 종료 시각을 가진다. 시작·종료 시각은 상태 변화가 관측된 수집 시각이다. 승강기 없이는 존재할 수 없고, 복구 전에는 종료 시각이 비어 있다. (11/17 01:42 수집까지 76건, 모두 진행 중)

⑦ 승하차 기록은 역·일자·시간대로 구분하며 전체 승차·하차 인원과 노인 승차·하차 인원을 가진다. 역 없이는 존재할 수 없다. 인원은 0 이상이고 노인 인원은 전체 인원을 넘지 않는다. 원천에 없는 인원은 비워 둔다. (1,993,840행)

⑧ 출입구 폐쇄는 폐쇄번호로 식별하며 폐쇄 장소, 시작일, 종료일, 사유, 대체 경로, 처음·마지막 관측 시각을 가진다. 같은 역·장소·시작일·대체 경로의 폐쇄는 한 건이다. 출입구 폐쇄는 반드시 하나의 역에 속한다. (8건)

⑨ 분석 회차는 회차번호로 식별하며 실행 시각, 군집 수, 입력 지표, 실루엣 계수, 사용한 승강기 수집 자료의 마지막 시각을 가진다. 분석 결과는 회차와 역사로 구분하며 군집 번호, 군집 이름, 우선 관리 순위, 우선 관리 점수를 가진다. 분석 결과는 회차와 역사 없이는 존재할 수 없다. (1회차, 결과 239건)

⑩ 모든 수집·적재 작업은 적재번호로 식별하며 출처, 실행 시각, 처리 행 수, 결과, 메시지를 가진다. 같은 출처·같은 실행 시각의 기록은 한 건이다.
