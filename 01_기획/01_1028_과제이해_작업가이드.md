## 1. 개념 정리 — 헷갈렸던 질문들

### Q1. 이 프로젝트가 기계학습 프로젝트와 뭐가 다른가? 실시간 입출력이 전부인가?

실시간성은 부차적이다. 차이는 **무엇을 결과물로 평가받느냐**에 있다.

| 구분 | 기계학습 과제 | 이 프로젝트(정보시스템) |
|---|---|---|
| 데이터 출발점 | CSV 하나를 그대로 불러옴 | 여러 출처 데이터를 **설계한 스키마**에 나눠 저장 |
| 핵심 산출물 | 모델과 정확도 | **DB 설계(ER·정규화)** + 질의 + 그 위에서 돌아가는 프로그램 |
| 데이터 결합 | pandas로 그때그때 merge | **FK로 관계를 정의**하고 SQL JOIN으로 결합 |
| 재사용 | 노트북을 다시 실행 | 새 데이터를 INSERT하면 **같은 프로그램이 같은 질의로 결과를 다시 계산** |
| 사용자 | 분석가 본인 | 특정 도메인의 의사결정자(예: 구청 담당자, 공장 안전관리자) |
| 모델의 위치 | 주인공 | 파이프라인 속 **한 단계** |

정리하면 "모델 하나 잘 만들기"가 아니라 **데이터를 구조화해 저장하고(DB), 필요한 걸 질의로 꺼내고(SQL), 가공해서(모델), 사람이 쓸 정보로 내놓는 체계 전체**를 만드는 일이다. 그래서 평가 비중은 모델 성능보다 설계 절차를 지켰는지, 문제가 그럴듯한지에 실린다.

### Q2. 공공데이터 = 오픈소스 데이터인가? 캐글은 안 되나? 예시가 외국 데이터던데?

- **공공데이터** = 정부·지자체·공공기관이 생산해 개방한 데이터(공공데이터법 기준). "누구나 받을 수 있는 데이터" 전체를 뜻하는 말이 아니다.
- **외국 데이터 가능**: 과제 예시가 data.gov(미국 정부)이므로 해외 정부 데이터도 공공데이터로 인정된다고 보는 게 자연스럽다.
- **캐글**: 데이터를 올려두는 플랫폼일 뿐이다. 판단 기준은 **원출처**다.
  - 원출처가 공공기관인 캐글 데이터(예: NYC 택시, 시카고 범죄, 서울시 따릉이 재업로드) → 사용 가능. 보고서에는 **원출처 기관**을 인용하고, 가능하면 원출처에서 직접 받는다.
  - 개인이 크롤링·합성한 데이터나 대회용 가공 데이터 → 공공데이터로 보기 어렵다. 피한다.
- 애매하면 교수님께 메일 한 줄로 확인한다(아래 결정 D3).

국내 주요 출처: 공공데이터포털(data.go.kr), KOSIS, 서울 열린데이터광장(data.seoul.go.kr), 기상자료개방포털(data.kma.go.kr), 지방행정 인허가데이터(localdata.go.kr), 각 부처 통계 사이트.

### Q3. "DB를 이용한 데이터 분석 모델링"은 무엇을 원하는가?

과제 문구는 `SQL 질의(데이터 도출) → 분석 모델링(AI 기법, 기계학습 등) 및 시각화 → 정보 도출`이다. 순서가 핵심이다.

1. **모델의 입력을 SQL로 만든다.** 예: 지역별 충전소 수와 전기차 등록 대수를 JOIN·GROUP BY로 한 표로 뽑는 것 자체가 특징(feature) 생성이다.
2. **Python에서 그 결과로 모델을 돌린다.** 회귀(수요 예측), 군집(지역 유형 분류), 분류(위험 등급) 같은 간단한 모델이면 충분하다. "등"이라고 되어 있으므로 통계 분석도 가능하지만, 안전하게 ML 모델 1개 이상을 넣는다.
3. **(권장) 모델 결과를 다시 DB에 저장한다.** `prediction` 같은 테이블을 만들어 INSERT하면 "DB 중심 정보시스템"이라는 성격이 분명해진다. ML 과제와 가장 크게 갈리는 지점이다.
4. **시각화로 "그래서 어떻게 하라는 것인지"를 보여 준다.** 예: "충전소 증설 우선순위 상위 10개 구".

### Q4. 삽입 SQL(Embedded SQL)이란? — 7장 p.120~126

- 정의: **프로그래밍 언어로 작성한 응용 프로그램 안에 넣어서 실행하는 SQL**.
- 교재는 C 언어 방식(`EXEC SQL`, 호스트 변수 `:p_no`, 커서 `DECLARE/OPEN/FETCH/CLOSE`)으로 설명한다.
- 실무와 이번 과제에서는 **Python + pymysql** 같은 DB 드라이버로 같은 개념을 구현하면 된다. 대응 관계를 보고서에 표로 적어 주면 "삽입 SQL을 이해하고 썼다"는 것이 드러난다.

| 교재(C, ESQL) | Python(pymysql) |
|---|---|
| `EXEC SQL CONNECT` | `conn = pymysql.connect(...)` |
| 호스트 변수 `:p_no` | 파라미터 바인딩 `%s` |
| `EXEC SQL DECLARE c CURSOR FOR SELECT…` / `OPEN` | `cur = conn.cursor(); cur.execute("SELECT…", (값,))` |
| `EXEC SQL FETCH c INTO :a, :b` (반복) | `for row in cur.fetchall():` / `cur.fetchone()` |
| `EXEC SQL CLOSE c` | `cur.close()` |

```python
import pymysql
conn = pymysql.connect(host="localhost", user="root", password="****", db="project_db", charset="utf8mb4")
with conn.cursor() as cur:
    region = input("지역명을 입력하세요: ")
    cur.execute("""
        SELECT r.region_name, COUNT(s.station_id) AS station_count
        FROM region r JOIN charging_station s ON r.region_code = s.region_code
        WHERE r.region_name = %s
        GROUP BY r.region_name
    """, (region,))                 # 사용자 입력 → SQL 변수 (호스트 변수 역할)
    for row in cur.fetchall():      # 커서로 여러 행을 하나씩 처리
        print(row)
```

## 3. 좋은 데이터 고르는 감각

### 3.1 체크리스트 (후보 데이터마다 O/X로 채워 보기)

| # | 기준 | 왜 중요한가 |
|---|---|---|
| 1 | **2개 이상 테이블로 나뉘고 공통 키로 연결된다** (지역코드, 날짜, 시설ID 등) | ER 다이어그램·FK·정규화를 보여 줄 재료. 표 하나짜리면 설계할 게 없다 |
| 2 | **원자료(행 단위) 수준**이다. 예: 충전소 1곳 = 1행 | "시도별 연간 합계 17행" 같은 요약 통계는 분석할 것도 설계할 것도 없다 |
| 3 | 수천~수십만 행 | 너무 적으면 모델이 의미 없고, 수백만 행 이상이면 로컬 MySQL 적재가 힘들다 |
| 4 | **시간 또는 공간 차원**이 있다 | 추세·예측·지도 시각화가 가능해진다 |
| 5 | 최근(2024~2025년)까지 갱신된다 | 참신성("최신 현황") 근거 |
| 6 | **CSV 파일로 바로 다운로드**된다 | 오픈API는 키 발급 대기와 호출 코드 작성 시간이 든다. 파일데이터 우선 |
| 7 | 반복되는 값이 있어 정규화할 거리가 있다 | 예: 원본 CSV에 "주소·운영기관명·운영기관전화"가 매 행 반복 → 운영기관 테이블로 분리 = 정규화 시연 |
| 8 | 답하고 싶은 질문이 바로 떠오른다 | 질문이 안 떠오르는 데이터는 버린다 |

7번이 특히 중요하다. **공공데이터 원본은 대개 비정규형(한 장짜리 큰 표)이므로, 이를 쪼개는 과정 자체가 8·9장 절차를 보여 주는 핵심 내용이 된다.**

### 3.2 데이터 확인 절차 (주제 확정 전 30분 테스트)

1. 출처 사이트에서 CSV를 내려받는다 → `프로젝트/data/raw/`에 저장
2. Claude에게 "이 CSV들 구조 보고 체크리스트 채워 줘"라고 요청한다 (Claude가 직접 열어서 행 수, 컬럼, 결측, 공통 키를 확인할 수 있다)
3. 공통 키로 JOIN했을 때 매칭률이 충분한지 본다 (예: 지역명 표기 불일치 "서울특별시" vs "서울")
4. 통과하면 주제 확정

### 3.3 어느 수준이면 "문제를 해결했다"고 할 수 있나

판단 기준은 행 수보다 **결정 단위와 데이터 단위가 맞는가**다.
- 결정 단위: 사용자가 실제로 고르는 대상. 예: "어느 **구**에 충전소를 늘릴까"라면 구 단위, "어느 **대여소**에 자전거를 옮길까"라면 대여소 단위
- 데이터는 결정 단위보다 **같거나 더 잘게** 있어야 한다. 시도별 합계로 구를 고를 수는 없다
- 모델에 들어가는 행(결정 단위 × 기간)이 최소 수백 개는 되어야 한다. 서울 25개 구 × 1년 = 25행이면 모델로는 부족하다. 행정동(약 420개)이나 대여소(약 2,700개) × 월 단위로 늘린다

| 수준 | 모습 | 평가 예상 |
|---|---|---|
| 하 | 표 1~2개, 단순 조회와 막대그래프 | 정보시스템이라 보기 어려움 |
| 중 | 출처 2~3개를 JOIN, 지표 생성(예: 전기차 1천 대당 급속충전기 수), 간단한 모델 | 기본 충족 |
| 상 | 중 + 모델 결과를 DB에 저장 + 사용자가 입력하면 그에 맞는 결과가 나옴 + 검증(예: 2024년 데이터로 학습해 2025년 실제값과 비교) | 목표 |

규모 감각: 원자료(가장 큰 표) 1만~100만 행, 전체 원본 출처 3~4개, 정규화 후 테이블 5~8개(1:N 관계 여러 개 포함). 테이블이 10개를 넘으면 설명하고 구현하는 부담만 커진다.

### 3.4 정제는 필요한가 — 필요하고, DB가 정제를 강제한다

기계학습에서는 지저분한 데이터도 pandas에서 대충 넘어갈 수 있다. DB에 넣으려면 그럴 수 없다.
- PK가 있으면 중복 행이 거부된다 → 중복 제거가 필요하다
- FK가 있으면 존재하지 않는 지역코드가 거부된다 → "서울특별시"와 "서울" 같은 표기 통일, 코드 매핑이 필요하다
- 타입이 정해져 있으면 "2025.3.1"과 "2025-03-01"이 섞인 날짜, "50kW"처럼 단위가 붙은 숫자가 거부된다 → 형식 변환이 필요하다

이 과정에서 생긴 오류와 처리 방법은 보고서의 "구현·테스트" 내용이 된다(HW1의 삽입 오류 분석과 같은 방식).

### 3.5 시간·공간 데이터 저장과 시각화

| 차원 | 저장 (MySQL) | 질의 | 시각화 |
|---|---|---|---|
| 시간 | `DATE`, `DATETIME` | `GROUP BY YEAR(d), MONTH(d)`, `HOUR(t)`, 요일 | 선 그래프(추세), 히트맵(요일×시간) — matplotlib |
| 공간(점) | 위도·경도 `DECIMAL(9,6)` 또는 `POINT` | `ST_Distance_Sphere`로 거리 계산(예: 반경 1km 안의 충전소 수) | folium 지도(HTML), matplotlib 산점도 |
| 공간(면) | 행정구역코드(`CHAR(10)`)로 연결 | 코드로 JOIN 후 집계 | 단계구분도(시군구 경계 GeoJSON 필요) |

주의할 점:

- 행정구역 경계 파일(GeoJSON)은 별도로 구해야 한다(통계지리정보서비스 SGIS 등)
- Claude는 matplotlib으로 만든 PNG는 직접 열어 확인할 수 있지만, folium HTML 지도는 사용자가 브라우저로 확인해야 한다

## 3-1. 정규화 예시 — 전기차 충전소 데이터 (가상 예시, 실제 컬럼명은 다를 수 있음)

### ① 원본 CSV (비정규형: 한 장짜리 큰 표)

충전기 1대가 1행이다. 충전소와 운영기관 정보가 매 행 반복된다.

| 충전기ID | 충전소ID | 충전소명 | 주소 | 시도 | 시군구 | 위도 | 경도 | 운영기관 | 운영기관전화 | 충전기타입 | 출력kW | 설치연도 |
|---|---|---|---|---|---|---|---|---|---|---|---|---|
| C001 | S01 | 수원시청 | 수원시 팔달구 효원로 241 | 경기도 | 수원시 | 37.2636 | 127.0286 | 환경부 | 1661-9408 | 급속 | 100 | 2023 |
| C002 | S01 | 수원시청 | 수원시 팔달구 효원로 241 | 경기도 | 수원시 | 37.2636 | 127.0286 | 환경부 | 1661-9408 | 완속 | 7 | 2021 |
| C003 | S02 | 아주대병원 | 수원시 영통구 월드컵로 164 | 경기도 | 수원시 | 37.2795 | 127.0466 | ○○차지 | 1588-0000 | 급속 | 200 | 2025 |
| C004 | S03 | 판교역 | 성남시 분당구 판교역로 160 | 경기도 | 성남시 | 37.3948 | 127.1112 | 환경부 | 1661-9408 | 완속 | 7 | 2022 |

이상현상(정규화가 필요한 이유):
- **수정 이상**: 환경부 전화번호가 바뀌면 수천 행을 모두 고쳐야 한다. 하나라도 빠지면 데이터가 서로 어긋난다
- **삽입 이상**: 충전기가 아직 설치되지 않은 새 충전소나 새 운영기관은 넣을 수 없다(충전기ID가 비어 있으므로)
- **삭제 이상**: ○○차지의 마지막 충전기 C003을 지우면 ○○차지라는 운영기관 정보도 함께 사라진다

### ② 함수 종속 찾기 ("A를 알면 B가 하나로 정해진다" = A → B)

- 충전기ID → 충전소ID, 충전기타입, 출력kW, 설치연도
- 충전소ID → 충전소명, 주소, 위도, 경도, 시군구코드, 운영기관ID
- 운영기관ID → 운영기관명, 운영기관전화
- 시군구코드 → 시도, 시군구명

충전기ID → 충전소ID → 운영기관전화처럼 **건너서 정해지는 종속(이행적 함수 종속)**이 있으므로 3NF가 아니다. 종속마다 테이블을 하나씩 만든다.

### ③ 정규화 결과 (3NF) + 다른 출처 데이터 결합

| 테이블 | 속성 (PK 굵게, FK는 →) | 원래 어디서 왔나 |
|---|---|---|
| `region` 지역 | **region_code**, sido_name, sigungu_name | 행정구역코드표 |
| `operator` 운영기관 | **operator_id**, operator_name, operator_phone | 충전소 CSV에서 분리 |
| `charging_station` 충전소 | **station_id**, station_name, address, latitude, longitude, region_code → region, operator_id → operator | 충전소 CSV에서 분리 |
| `charger` 충전기 | **charger_id**, station_id → charging_station, charger_type, output_kw, install_year | 충전소 CSV에서 분리 |
| `ev_registration` 전기차 등록 | **region_code → region, base_month**, ev_count | **다른 출처**(자동차 등록 통계) |
| `population` 인구 | **region_code → region, base_year**, population, age65_ratio | **다른 출처**(주민등록 인구) |

관계(ER 다이어그램에 그릴 것):
- region 1 : N charging_station
- operator 1 : N charging_station
- charging_station 1 : N charger
- region 1 : N ev_registration, region 1 : N population

`region_code`라는 공통 키 하나로 출처가 다른 세 데이터가 묶인다. 3.1 체크리스트 1번이 말하는 연결이 이것이다.

### ④ 이 구조에서 나오는 질의 → 분석의 입력

```sql
-- 시군구별 전기차 1천 대당 급속충전기 수 (모델의 특징값이 됨)
SELECT r.sigungu_name,
       COUNT(c.charger_id) * 1000 / e.ev_count AS fast_charger_per_1000_ev
FROM region r
JOIN charging_station s ON s.region_code = r.region_code
JOIN charger c          ON c.station_id = s.station_id AND c.charger_type = '급속'
JOIN ev_registration e  ON e.region_code = r.region_code AND e.base_month = '2025-12'
GROUP BY r.region_code, r.sigungu_name, e.ev_count
ORDER BY fast_charger_per_1000_ev;
```

## 4. 참신성 확보 — 최신 이슈를 어떻게 잡을까

Claude의 지식은 2026년 6월경까지이고 이 세션에서는 웹 검색을 쓰지 않는다. 대신 **사용자는 브라우저를 쓸 수 있으므로**, 역할을 나눈다.

참신성은 "어제 뉴스"보다 아래 세 가지에서 나온다.

## 6. 8·9장 설계 절차 → 제안서에 쓸 "준수 항목"

과제 요구: "구체적 설계 절차 준수 항목은 제안서에 기술되어 있어야 함". 아래 표를 제안서에 거의 그대로 넣으면 된다.

| 단계 | 교재 정의 | 이 프로젝트에서 할 일 | 산출물 |
|---|---|---|---|
| 1. 요구사항 분석 | DB 용도 파악 | 사용자·업무 정의, 필요한 데이터·질의 목록 작성 | **요구사항 명세서** |
| 2. 개념적 설계 ★ | DBMS 독립 구조 | 개체·속성·관계·카디널리티(1:N 등) 도출 | **E-R 다이어그램** |
| 3. 논리적 설계 ★ | DBMS 적합 구조 | ER → 릴레이션 변환 규칙 적용, PK/FK 지정 | **릴레이션 스키마** |
| (9장) 정규화 검증 ★ | 이상현상 제거 | 원본 CSV의 함수 종속 분석 → 1NF·2NF·3NF(필요 시 BCNF) 확인 | 정규화 과정 표, 이상현상 예시 |
| 4. 물리적 설계 | 구현 가능한 구조 | 데이터 타입, 인덱스, 제약조건 결정 | 물리적 스키마 |
| 5. 구현 | SQL 실행 | CREATE TABLE·데이터 적재·VIEW | DDL 스크립트, 구축된 DB |

설계 중 오류를 발견하면 이전 단계로 되돌아갈 수 있다(교재 그림 8-1). 되돌아간 기록을 남겨 두면 보고서의 "설계 과정" 서술이 풍부해진다.

> 주의: 폴더의 PDF에는 8장 개요(그림 8-1, 8-2)만 있다. 9장 정규화(함수 종속, 정규형 정의) 강의자료가 나오면 이 폴더에 추가한다.

## 7. 제안서 작성 가이드 (MS-Word, 자유 양식, 마감 11/3)

파일명: `프로젝트-제안서-이름1-이름2.doc(x)`

작성 태도(사용자 첨언): **기획안을 쓴다고 생각한다.** 아직 하지 않은 일이므로 "~하겠다", "~할 예정이다"로 계획을 적으면 된다. 분량보다 **요구사항 하나하나가 어떻게 충족되는지 보이는 것**이 중요하다.

### 1) 프로젝트 제목 및 목적
- 제목은 구체적으로: 도메인 + 방법 + 결과. 예) "공공데이터 기반 시군구별 전기차 충전 인프라 수급 분석 및 증설 우선순위 정보시스템"
- 추진 배경: 최신 이슈 근거(기사 1~2개, 수치)
- 목적: 누가 어떤 결정을 내리도록 돕는가

### 2) 프로젝트 수행 내용, 범위, 예상 결과물
- **요구사항 충족 계획표** (아래 표를 그대로 사용)
