## 1. 주제 변천과 최종 방향

1. 처음 : 지하철 무임승차(월별 유·무임 데이터 중심)
2. 교수님 피드백 : "월별로 추가되는 데이터로 정보를 만들면 DB 구축이 아니라 데이터 분석 프로젝트가 된다"
3. 혼잡도는 분기 갱신이라 매일 데이터가 될 수 없음 → 매일 갱신 데이터를 찾아 175건 조사
4. **핵심 발견 : OA-22723 `getStnPsgr`** — 일자 × 시간 × 역 × 카드구분 × **사용자구분(일반/우대권=무임/청소년…)** 승하차, 매일 갱신(D-2), **원천이 최근 약 1주만 보관** → 매일 쌓지 않으면 사라짐 = DB를 구축·운영할 이유가 데이터 자체에 있음. 무임 주제도 일별로 살아남

### 최종 방향 (10/31 합의)

- **제목 방향** : 고령 이용객을 배려하는, 누구나 쓰는 지하철역 이용 정보 대시보드 (정식 제목 미정)
- **문제** : 고령 승객이 많은 역·시간대에 혼잡과 승강기 고장이 겹치지만, 무임(우대권) 정보는 월 단위로 늦게 공개되고 일별 원천은 1주 뒤 사라져 하루 단위 대비가 불가능
- **사용자** : 일반 이용자, 고령·교통약자, 역 관리자
- **대시보드 3구역**
  1. 오늘의 이용객 추정 : 시간대별 예상 이용객·예상 우대권 비율·혼잡 피크·덜 붐비는 시간
  2. 월별 추정(참고) : 이번 달 누적 무임 추정 vs 지난달 확정, 역별 무임 비율, 작년 대비
  3. 오늘의 승강기·출입구 : 고장 승강기·위치, 최근 30일 고장 횟수, 폐쇄 출입구·대체 경로
- **범위** : 서울교통공사 1~8호선 구간 (약 280개 역)

## 2. 생성 주기가 다른 데이터를 합치는 구조 : "기준일(as-of date)"

모든 화면은 사용자가 고른 **기준일** 하나로 계산한다. 실시간은 하지 않는다(베타 성격, 난이도 낮춤).

| 층 | 정의 | 데이터 | DB가 하는 일 |
|---|---|---|---|
| ① 오늘의 상태 | 기준일에 수집한 승강기·출입구 상태 | 승강기 가동현황, 출입구 임시폐쇄 | 하루 1회 스냅샷 → 상태 변화로 고장 이력 생성 |
| ② 최근 실측 | 기준일 − 2일까지 실제 이용 | `getStnPsgr` | 매일 적재, 1주 지난 원천을 대신 보존 |
| ③ 오늘 추정 | 같은 요일·시간 최근 4주 기준 + 모델 | ②에서 계산 | 예측을 예측일과 함께 저장, 실측 오면 오차 기록 |
| ④ 고정 기준 | 혼잡 패턴, 시설, 역 정보 | 혼잡도(분기), 시설·역 마스터 | 바뀔 때만 교체 |

- **월별 유·무임(OA-12251)** 은 ②의 월 합계와 대조하는 **정합성 검증 장치**로 쓴다 (교수님 피드백에 대한 답 : 월별 데이터는 일별 시스템의 검증·참고용)
- **시연** : (1) 발표일 기준 화면 — "최신 실측은 이틀 전, 오늘은 추정"을 그대로 표시, (2) 기준일 되감기 — 과거 날짜의 추정과 이후 실측 비교 = 15일 운영 증빙
- 운영 : 11월 초~12월 초 **실제 매일 적재** (재생 방식은 운영 요건에 약해서 쓰지 않음)
- 난이도 조정 : 승강기 하루 1회 수집, 매일 수동 실행 허용, 기준선은 4주 평균

## 4. 지금까지 확인한 사실 (검증됨)

### API (`getStnPsgr`)
- 일반 인증키로 호출 성공 (10/31). 키는 **메모·코드에 적지 말고 `.env`에 보관**
- URL : `http://openapi.seoul.go.kr:8088/{KEY}/json/getStnPsgr/{시작}/{끝}/{통행일자}/{역코드}/{역명}/{시간}` — **공백 없이**
- 조건은 순서대로 채워야 함 (중간 생략 시 0건) → 날짜만 넣고 하루치 전체 수집이 정석
- 1회 최대 1,000행 · 하루 약 6만 행(약 61회 호출) · 응답 `response.header.resultCode == "00"` 정상, `body.totalCount`
- 10/31 기준 조회 가능 범위 : 10/23~10/29 (D-2, 약 1주 보관)
- 역코드 예 : 강남 `0222`, 모란 `2827` (혼잡도 역번호와 같은 체계로 보임 — 숫자 비교로 확인 필요)
- 공식 한도 : 실시간 지하철 API만 하루 1,000회. 일반 키는 횟수 한도 안내 없음, 단 "제약 없이 계속 쓰려면 활용사례 등록" 문구 있음

### 로컬 데이터 (`03_연습프로젝트/data/raw/`)
- 혼잡도 3개 분기 : cp949, 44열(식별 5 + 시간대 39), 1,671행, 서울교통공사 1~8호선 282개 역번호. 3월 파일만 열 이름 다름(`요일구분`/`출발역`), 3·6월 값에 뒤 공백. 전 시간대 0인 행 42개(종점 방향 운행 없음)
- 월별 유·무임(2026-01~09) : **7월분 621행 완전 중복** (PK 필요성 사례), cp949로 `·`이 `?`로 깨짐
- 일별 승하차 `CARD_SUBWAY_MONTH_*` : 행 끝 빈 열, 연도별 인코딩 다름, 등록일 = 사용일 + 3일
- 9월 기준 유·무임 승차 합 = 일별 승차 합 **620개 역 오차 0** → 월·일 정합성 검증 가능
- 혼잡도 역명과 일별·월별 역명 일치 211/281 → 이름 매칭은 불완전, **역코드 기준으로 연결**

## 6. ER 1차 후보 (확정 아님)

```
노선 1──< 역(역코드 PK) 1──< 승강기 1──< 승강기_상태_스냅샷 (하루 1회, 일정 기간 후 삭제)
                    │                └──< 승강기_고장_이력 (시작일, 종료일)  ← 스냅샷 변화로 생성
                    ├──< 시간별_승하차 (일자, 시간, 사용자구분) ── 사용자구분 코드표
                    ├──< 이용_예측 (대상일, 시간, 예측일, 예측값, 실측값)
                    ├──< 출입구_폐쇄 (시작일, 종료일)
                    ├──< 월별_유무임 (사용월, 요금구분)
                    └──< 혼잡도 (요일, 방향, 시간대, 기준분기)
load_log (모든 적재·삭제 기록)
```

정규화 예정 사례 : 혼잡도 가로형 → 세로형(1NF) · 카드구분·사용자구분 반복 → 코드 테이블(2NF·3NF) · 월별 유·무임 4개 열 → 세로형
