# 물리 스키마 (2026-11-17, 실제 DB 기준)

논리 스키마(`03_릴레이션스키마.md`)를 MySQL에 구현한 결과이다. 테이블 정의의 원본은 `03_sql/01_schema.sql`이며, 이 문서의 행 수·용량·실행 시간은 2026-11-17 01:30~01:46에 `subway_access_db`를 직접 조회한 값이다. 11/17 13:28 3차 스키마(CLUSTER_TYPE 분리, OUTAGE.start_known 추가)로 다시 생성한 뒤 바뀐 테이블(OUTAGE, CLUSTER_TYPE, CLUSTER_RESULT, LOAD_LOG)의 행 수는 13:31 재적재 기준으로 갱신하였다. 11/25에 CLUSTER_RUN.features를 RUN_FEATURE로 분리하고 ck_ridership_senior_alight를 추가했으며(2.14절), 이 변경 이후 테이블은 14개이다.

| 열 | 타입 | NULL | 키 | 기본값 | 제약 | 설명 |
|---|---|---|---|---|---|---|
| elevator_no | INT UNSIGNED | N | PK, FK → ELEVATOR (ON DELETE CASCADE), UK(elevator_no, start_at) | | | 승강기 |
| seq | SMALLINT UNSIGNED | N | PK | | | 승강기별 순번(1부터) |

| start_known | TINYINT UNSIGNED | N | | 1 | CHECK 0, 1 | 시작 시각 확실성. 승강기의 첫 관측에 이미 비가동이거나, 그 승강기의 직전 관측과 70분(수집 공백 기준)보다 더 벌어진 뒤 비가동이 처음 보이면 0(실제 시작 모름, 통계 제외), 70분 이내의 가동 관측 직후 시작이면 1. 실측(11/17 14:08 재계산) 0이 94행(ES 86, EV 8: 첫 관측 75 + 02:00→11:40 공백 직후 19), 1이 5행 |

인덱스: PRIMARY(elevator_no, seq), uk_outage_start(elevator_no, start_at), ix_outage_open(end_at). 행 수 99(13:00 수집 반영 후, 진행 중 93행).

start_known은 BOOLEAN 대신 TINYINT UNSIGNED + CHECK로 두었다. MySQL의 BOOLEAN은 TINYINT(1)의 별칭이어서 2 이상의 값도 들어가므로, 0·1만 허용하도록 CHECK를 명시한다. 기본값 1은 수집이 끊기지 않고 이어지는 동안 새로 생기는 구간이 시작 시각을 아는 구간이기 때문이다. 다만 수집 공백(PC 꺼짐 등) 직후나 승강기가 응답에서 빠졌다가 다시 나타난 직후에 처음 보인 비가동은 실제 시작이 그 사이 어딘가이므로 0으로 둔다. 공백 기준 70분은 `05_코드/preprocess.py`의 `GAP_MINUTES`와 `v_collect_gap`이 같은 값을 쓴다. 수집 공백과 겹치는지(gap_overlap)는 저장하지 않고 `v_outage`에서 LOAD_LOG로부터 계산한다.

## 3. 타입 선택 이유

| 대상 | 선택 | 이유 |
|---|---|---|
| 역번호·역사번호 | SMALLINT UNSIGNED (2바이트) | 실측 최대 2828로 0~65,535 범위에 든다. RIDERSHIP 199만 행의 기본키 첫 열이므로 INT(4바이트)보다 행과 인덱스가 작다. 4자리 문자 역코드("0150")가 아닌 정수로 두어 승하차 자료의 역번호와 그대로 비교한다. |
| 노선·시간대·군집 번호 | TINYINT UNSIGNED | 값 범위가 1~8, 5~24, 1~6이다. |
| 인원 | INT UNSIGNED | 시간대 1칸 실측 최대 26,951로 SMALLINT UNSIGNED(최대 65,535)에도 들지만 여유가 2.4배뿐이다. 다른 연도나 일 합계를 같은 형식으로 넣을 수 있도록 INT로 둔다. 음수가 없으므로 UNSIGNED. |
| 평균 인원 | DECIMAL(9,1) | 평균은 소수가 생긴다. 실측 최대 24,046.5. FLOAT의 반올림 오차를 피하려고 고정소수점을 쓴다. |
| 정거장 깊이 | DECIMAL(5,2) | 원천이 소수 둘째 자리(−19.07)까지 준다. 표현 범위 ±999.99, 실제 허용 범위는 CHECK −50~100으로 제한한다. 고가역 24개가 음수이므로 UNSIGNED를 쓰지 않는다. |
| 위도·경도 | DECIMAL(9,6) | 원천이 소수 여섯째 자리까지 준다(약 0.1m 단위). |
| 수집 시각 | DATETIME | 수집기는 +09:00 시간대가 붙은 시각을 기록하며, 정제 단계에서 시간대 표시를 떼고 한국 시각 그대로 저장한다. TIMESTAMP는 세션 시간대에 따라 변환되므로 쓰지 않는다. |
| 종류·요일구분 | CHAR(2) | 값이 'EV'/'ES', '평일'/'주말'로 길이가 고정이다. utf8mb4에서 CHAR(2)는 2문자이다. |
| 이름·장소 문자열 | VARCHAR(10~100) | 실측 최대 길이(승강기명 40자, 폐쇄 장소 26자, 역명 16자)보다 크게 잡아 원천 값이 길어져도 잘리지 않게 한다. |

## 4. 인덱스 선택 이유

InnoDB는 기본키 순서로 행을 저장한다(클러스터형 인덱스). 기본키는 가장 많이 쓰는 조회 조건을 앞에 두도록 정하였다.

| 인덱스 | 대상 질의 | 이유와 확인 |
|---|---|---|
| RIDERSHIP PRIMARY(station_no, ride_date, hour_slot) | 한 역(역사)의 시간대별 이용, PROFILE 재계산 | 한 역의 1년 7,300행이 연속 저장된다. `EXPLAIN ... WHERE station_no = 423 GROUP BY hour_slot`은 type = ref, key = PRIMARY, key_len = 2로 기본키 앞부분만 읽는다. 적재도 이 순서로 정렬하여 넣는다. |
| RIDERSHIP ix_ridership_date(ride_date) | 특정 기간의 전 역 집계(주간·월별 추이) | 기본키 첫 열이 역번호여서 날짜 조건만으로는 기본키를 쓸 수 없다. `EXPLAIN ... WHERE ride_date BETWEEN '2025-03-01' AND '2025-03-07'`은 type = range, key = ix_ridership_date이다. 비용은 인덱스 27.55MB(테이블 데이터 85.63MB). |
| RIDERSHIP_PROFILE PRIMARY(complex_id, day_type, hour_slot) | 대시보드에서 역사를 고르면 평일·주말 시간대 그래프 조회 | 역사 1개·요일구분 1개 = 20행을 기본키 범위로 읽는다. |
| OUTAGE PRIMARY(elevator_no, seq) | 승강기별 이력, 현재 상태 조인(v_elevator_now) | 조인 조건 elevator_no가 기본키 첫 열이다. |
| OUTAGE ix_outage_open(end_at) | 진행 중인 비가동 목록(end_at IS NULL), 복구 시각 범위 조회 | 수집 기간이 길어지면 종료된 구간이 대부분을 차지하므로 진행 중인 구간만 골라 읽는다. 11/17 13:31 기준 99행(2.6절)이라 효과가 작다. |
| STATION ix_station_complex(complex_id) | 역사 → 소속 역 조회, 역사 단위 집계의 조인 | 모든 역사 단위 뷰가 station.complex_id로 묶는다. 외래키 열이기도 하다. |
| STATION ix_station_line(line_no) | 노선별 역 목록 | 외래키 열. InnoDB는 외래키 열에 인덱스가 필요하다. |
| UNIQUE: uk_line_nm, uk_complex_nm, uk_station_fr_code, uk_station_line_nm, uk_elevator_name, uk_elevator_fclt, uk_outage_start, uk_closure, uk_load | 대체키의 유일성 보장(강의는 대체키를 UNIQUE로 지정, 07장 p.13), 자연키 중복 방지, UPSERT의 충돌 판단 | `INSERT ... ON DUPLICATE KEY UPDATE`는 PK·UNIQUE 충돌로 기존 행을 찾는다. 대리키 테이블(ELEVATOR, EXIT_CLOSURE, LOAD_LOG)은 이 UNIQUE가 없으면 재적재 때마다 행이 늘어난다. uk_load(source, run_at)는 수집 공백 조회(`v_collect_gap`, `02_checks.sql` 7-3)와 마지막 수집 시각 조회에도 쓰인다. |
| CLUSTER_RESULT ix_cluster_type(run_id, cluster_no) | 군집별 역사 목록, CLUSTER_TYPE 조인(v_cluster_latest) | 복합 외래키 (run_id, cluster_no)의 참조 열 순서와 같은 인덱스가 InnoDB에 필요하다. 기본키 (run_id, complex_id)는 첫 열만 같아 쓸 수 없다. |

만들지 않은 인덱스: RIDERSHIP.hour_slot(값이 20가지뿐이고 시간대 조건은 역·날짜 조건과 함께 쓰인다), ELEVATOR.kind(값 2가지), LOAD_LOG.result. 선택도가 낮아 전체 읽기와 차이가 작고, RIDERSHIP에 인덱스를 더하면 적재 시간과 용량이 늘어난다.

## 5. 적재 방식

### 5.1 흐름

```
원천(07_데이터/raw, 07_데이터/snapshots) → preprocess.py → 07_데이터/clean/*.csv → load_db.py → MySQL
```

| 단계 | 방식 |
|---|---|
| 적재 순서 | line → station_complex → station → transfer → elevator → ridership → exit_closure → load_log → outage → ridership_profile. 부모 테이블을 먼저 넣어 외래키 위반이 생기지 않게 한다. |
| 기본 방식 (UPSERT) | `INSERT INTO t (...) VALUES (...) ON DUPLICATE KEY UPDATE 키가 아닌 열 = VALUES(열)`. 5,000행씩 묶어 실행한다. 같은 CSV를 다시 넣으면 기존 행이 같은 값으로 갱신되어 행 수가 늘지 않는다. |
| 트랜잭션 | 테이블 1개 = 트랜잭션 1개. 오류가 나면 그 테이블을 롤백하고, LOAD_LOG에 result = 'error'와 오류 메시지를 남긴 뒤 중단한다. |
| 매시 반영 (`--live`) | 수집분에 해당하는 elevator, exit_closure, load_log, outage만 다시 정제·적재한다. 승하차와 PROFILE은 다시 계산하지 않는다. |

### 5.2 OUTAGE 재계산

비가동 구간은 전체 스냅샷을 처음부터 다시 훑어 계산한다(`preprocess.outage_intervals`). 이전 결과에 이어 붙이지 않으므로 계산 규칙을 바꾸거나 늦게 들어온 스냅샷이 있어도 결과가 일관된다. 적재는 다음 순서이다.

1. 정제 결과의 (역번호, 승강기명)을 ELEVATOR에서 찾아 elevator_no로 바꾼다. 찾지 못한 행이 1건이라도 있으면 오류로 중단한다.
2. 같은 트랜잭션 안에서 `DELETE FROM outage` 후 전체를 다시 넣는다. start_known도 매번 스냅샷 전체에서 다시 계산하므로, 서버 스냅샷처럼 더 이른 수집분이 나중에 합쳐지면 그 결과에 맞게 바뀐다.

ELEVATOR는 (station_no, elevator_nm) UNIQUE로 UPSERT되므로 이미 있는 승강기의 elevator_no는 재적재해도 바뀌지 않는다. 다만 InnoDB의 AUTO_INCREMENT는 충돌로 갱신된 행에도 번호를 소비한다(innodb_autoinc_lock_mode = 2). 실제로 ELEVATOR를 2,750행씩 세 번 적재한 뒤 다음 AUTO_INCREMENT 값은 8,252였고, LOAD_LOG의 load_id는 20 다음이 30, 35 다음이 45로 건너뛰었다. 번호가 비는 것은 무결성에 영향이 없다. 매시 2,750개씩 소비해도 1년에 약 2,409만 개로 INT UNSIGNED 범위(약 42.9억)에 비해 작다.

### 5.3 RIDERSHIP_PROFILE 재계산

`DELETE FROM ridership_profile` 후 `INSERT ... SELECT` 한 문장으로 다시 채운다. 안쪽 질의는 RIDERSHIP과 STATION을 조인해 역사·일자·시간대별 합계를 만들고, 바깥 질의는 이를 역사·요일구분·시간대로 묶어 자료가 있는 날 수로 나눈다. 요일구분은 `DAYOFWEEK(ride_date) IN (1, 7)` 또는 2025년 공휴일 목록에 들면 '주말'이다. 승하차 적재 직후 같은 실행에서 수행하며, 11/17 적재에서 RIDERSHIP 적재 완료(01:33:09)부터 PROFILE 완료(01:33:35)까지 약 26초가 걸렸다.

### 5.4 수집 스냅샷과 LOAD_LOG

수집기(`collect.py`)는 DB에 직접 쓰지 않고 스냅샷 파일과 `collect_log.csv`만 남긴다. 정제 단계가 수집 기록 가운데 스냅샷 파일이 있는 행과 실패 행을 골라 LOAD_LOG에 넣으며, (source, run_at) UNIQUE로 같은 스냅샷이 두 번 기록되지 않는다. 파일 적재는 테이블마다 source = 'file:테이블명'으로 1행씩 남긴다.
