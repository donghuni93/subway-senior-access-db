## ③ 정제 — 서로 다른 자료를 같은 역으로 맞춘다

`05_코드/preprocess.py` → `07_데이터/clean/*.csv`, 매칭 실패 기록 `07_데이터/clean/unmatched.csv`(현재 3건, 모두 설명 가능)

**역 식별 (가장 중요한 발견)**
- 승하차 자료의 "역번호"는 승강기 API의 **역코드(STN_CD)를 정수로 쓴 값**이다(서울역 0150 → 150, 방화 2511). 처음에는 외부코드(서울역 133)로 보고 매칭해 278개 중 113개만 연결되었고, 값을 대조해 바로잡은 뒤 278개 모두 연결되었다.
- 역명으로만 주어지는 자료(좌표·건축·환승·심도·출입구 폐쇄)는 (호선, 정규화한 역명)으로 찾는다. 역명 변경(당고개→불암산, 미아삼거리→미아사거리 등 5곳)과 심도 파일의 줄임·오기 표기(을지3가, DMC, 애오게 등 9곳)는 호선별 별칭표로 처리했다.

**역사(驛舍) 묶음 — 환승역 처리**
- 문제: 환승역은 승하차·승강기가 한 호선 코드로만 기록된다. 3호선 충무로는 승하차 20일·승강기 0대(4호선에 합산), 5호선 청구는 승강기 0대(6호선에 기록).
- 해결: 같은 건물의 호선별 역을 **역사**로 묶는다. 278개 역 → 242개 역사(다호선 역사 34개: 2개 호선 32곳, 3개 호선 2곳(종로3가·동대문역사문화공원)). 규칙은 "정규화 이름이 같으면 같은 역사", 예외로 4호선 총신대입구 ↔ 7호선 이수.
- 확인: 8호선 암사와 암사역사공원은 서로 다른 역이다(처음에 같은 역으로 잘못 묶었다가 바로잡음).

**변환**
- 승하차: 시간대 20개 열(06시 이전 ~ 24시 이후) → 행으로 펼치고(hour_slot 5~24), 노인과 전체를 (역, 일자, 시간대)로 합친다.
- 비가동 이력: 매시 스냅샷을 시간순으로 보며 `사용가능`이 아닌 구간을 뽑는다. 시작 = 처음 비가동 관측 시각, 종료 = 다시 사용가능 관측 시각, 수집이 빠진 시각은 구간을 바꾸지 않는다.
- 출입구 폐쇄: 매시 관측을 (역, 장소, 시작일, 대체 경로)로 합치고 처음·마지막 관측 시각을 남긴다.
- 역사심도의 음수 24개 역은 **고가역**(승강장이 지상보다 높음)이다. 부호를 유지하고 수직 이동 부담은 절댓값으로 본다.

## ④ DB 설계·적재 — subway_access_db

**스키마** (`03_sql/01_schema.sql`, 그림 `02_설계/ERD.png`): 테이블 12개

| 구분 | 테이블 | 행 수 |
|---|---|---|
| 기준 | LINE, STATION_COMPLEX(역사), STATION, TRANSFER | 8 / 242 / 278 / 140 |
| 승강기 | ELEVATOR, OUTAGE(비가동 이력, 약한 개체) | 2,750 / 76 (수집이 쌓이며 증가) |
| 수요 | RIDERSHIP(역·일자·시간대) | 1,993,840 |

| 분석 | CLUSTER_RUN, CLUSTER_RESULT | 1회차 / 239 |
| 성능용 집계 | RIDERSHIP_PROFILE(역사 × 평일/주말 × 시간대 평균) | 9,620 |
| 관리 | LOAD_LOG(수집 스냅샷·적재 실행 기록) | 수집마다 증가 |

**제안서 대비 바뀐 설계**

| 항목 | 제안서 | 구현 | 이유 |
|---|---|---|---|
| 역 묶음 | 없음 | STATION_COMPLEX 추가 | 환승역 기록이 한 호선에 몰림 |
| 역 키 | 역번호(외부코드 가정) | 역코드 정수 + 외부코드는 별도 UNIQUE | 승하차 역번호 = 역코드 |
| 환승 | 역–역 M:N 순환 | (역, 환승 노선명) | 환승 대상에 범위 밖 노선(공항철도 등)이 섞임 |
| 승강기 키 | 원천 ID 가정 | 대리키 + UNIQUE(역, 승강기명) | 가동현황 API에 ID 없음 |
| 승강기 높이 | height_m | 제외 | 자료 확보 실패 |
| 분석 결과 | 역 단위 | 역사 단위 + 분석 회차 테이블 | 환승역 왜곡 방지, 재실행 이력 보존 |
| 집계 테이블 | 없음 | RIDERSHIP_PROFILE | 199만 행을 화면마다 집계하지 않기 위한 의도적 파생 테이블 |

**적재** (`05_코드/load_db.py`, 삽입 SQL)
- pymysql로 `INSERT ... ON DUPLICATE KEY UPDATE`를 5,000행씩 실행한다. 같은 CSV를 다시 넣어도 행 수가 같다(확인함).
- OUTAGE는 스냅샷 전체에서 다시 계산한 결과로 바꿔 넣고, RIDERSHIP_PROFILE은 적재 후 SQL로 다시 계산한다(2025년 공휴일 17일은 주말로 봄).
- DB 접속은 기존 MySQL login-path `endb`를 읽는다. 비밀번호를 코드·`.env`에 두지 않는다.
- 기존 `subway_db`(HW2 실습용)는 건드리지 않았다.

## ⑥ 군집 분석 — 질문 3

`05_코드/analysis.py` → CLUSTER_RUN·CLUSTER_RESULT, `04_결과/csv/군집/cluster_summary.csv`, `priority_ranking.csv`, `cluster_k_selection.csv`

- 대상: 승하차 100일 이상·승강기가 있는 역사 239개(까치울·상동 등 관리 구간 밖 제외)

| 2. 환승 부담 작음 | 159 | 노인 비중 18.6%로 가장 높음, 깊이 15.5m |

## ⑨ 자동 갱신 — 수집이 바로 DB와 화면에 반영된다
