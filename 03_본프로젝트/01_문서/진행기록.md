## 2026-11-17 / 계획

**무엇을 했나.** 최종 제출 제안서(11/3)를 기준으로 12/10까지의 팀 할 일을 0~5단계로 다시 정리하여 `README.md` 진행표를 교체하였다. 이전 진행표는 제안서 확정 전 주제(이용객 수 예측 모델) 기준이어서 최종 제안서의 세 질문·군집 분석과 맞지 않았다.

**확인한 상태.** 제안서 일정상 11/10에 시작했어야 할 승강기 가동현황(매시)·출입구 임시폐쇄(매일) API 수집이 아직 시작되지 않았다. 설계(11/4~9)와 구축(11/10~18)도 시작 전이다.

**결정 1. 원본 스냅샷을 먼저 수집한다.** 지난 시간의 승강기 상태는 나중에 받을 수 없으므로, 스키마 확정을 기다리지 않고 API 원본 응답을 시각별 JSON 파일로 저장하는 수집기부터 가동한다. OUTAGE·EXIT_CLOSURE 변환은 설계가 확정된 뒤 이 파일을 다시 읽어 수행한다. 설계가 바뀌어도 수집한 데이터를 잃지 않는다.

**결정 2. 수집 기간을 11/18~12/8로 바꾼다.** 제안서는 11/10~12/1 3주 수집을 계획하였다. 시작이 늦어진 만큼 종료를 12/8로 미루어 3주를 지킨다. 12/3 발표는 그때까지 모인 약 2주분으로 하고, 최종보고서에 3주분을 반영한다. 제안서 표 9의 "12.4~12.10 3주 수집 결과 반영"과 맞는다.

**결정 3. 담당은 제안서 표 8을 따른다.** 이동훈은 설계·DB·SQL, 박재연은 수집·정제·분석, 대시보드와 보고서는 공동이다. 수집기 첫 가동은 일정상 바로 하고, 매일 운영을 누가 맡을지는 팀에서 정한다.

## 2026-11-17 01시 / 0단계 수집 시작

**무엇을 했나.** 인증키를 `.env`에 넣고 승강기·출입구 API 3종을 실제 호출하여 필드와 값을 확인하였다(`02_설계/00_API확인.md`). 원본 수집기 `05_코드/collect.py`를 작성하고(단위 테스트 7개 통과) Windows 작업 스케줄러에 `ENDB_SubwayCollect`로 등록하였다. 11/17 00:57 수동 실행으로 3종 모두 API 전체 건수만큼 받은 것을 확인하였고, 01:00부터 매시 실행된다.

**왜 그렇게 결정했나.**
- 승강기 API를 2종 수집한다. OA-15994는 에스컬레이터까지 포함하지만 승강기 ID가 없고, OA-22740은 엘리베이터만 있지만 시설번호와 역번호가 있다. 둘을 함께 쌓아 두면 설계 단계에서 어느 쪽을 OUTAGE의 원천으로 삼을지 다시 정할 수 있다.
- 출입구 폐쇄도 매시 수집한다. 8건뿐이라 부담이 없고, 작업을 하나로 두는 편이 운영 실수가 적다.
- 원본을 gzip으로 저장한다. 비압축 시 1회 약 1MB로 3주 약 500MB가 OneDrive에 쌓이기 때문이다(압축 후 약 30MB).

**문제와 해결.**
- 수집기 테스트에서 가짜 응답의 서비스명을 잘못 넣어 1건 실패하였다. 테스트를 고치면서, 응답 형식이 예상과 다를 때 "None None"만 남던 오류 메시지를 응답의 최상위 키를 보여 주도록 바꾸었다.
- 작업 스케줄러 실행 파일(`run_collect.cmd`)은 한글 경로 인코딩 문제를 피하려고 자기 위치(`%~dp0`)만 쓰고, 파이썬은 OneDrive 밖의 가상환경 경로를 직접 호출한다.

**남은 위험.** PC가 꺼지거나 절전 중인 시간은 수집되지 않는다. 수집을 어느 PC에서 계속할지 팀에서 정해야 한다.

## 2026-11-17 01~02시 / 1·2단계 앞당겨 진행 (전처리, DB 구축, ERD)

**무엇을 했나.**

- 무결성 점검 `03_sql/02_checks.sql`: 고아 행·값 범위·기간 역전 모두 0. 같은 CSV를 다시 적재해도 행 수가 같음을 확인.
- ERD를 Mermaid(`02_설계/02_ER다이어그램.md`)와 그림(`02_설계/ERD.png`, DB 스키마에서 자동 생성하는 `05_코드/draw_erd.py`)으로 만들고, 릴레이션 스키마(`02_설계/03_릴레이션스키마.md`), 데이터 검사(`02_설계/00_데이터검사.md`)를 작성하였다.

**왜 그렇게 결정했나.**
- DB 이름을 `subway_access_db`로 새로 만들었다. 기존 `subway_db`는 HW2(혼잡도·연결통로) 실습용이라 건드리지 않았다.
- DB 접속은 기존 login-path `endb`를 `myloginpath`로 읽는다. 비밀번호를 코드·.env에 두지 않기 위해서다.
- 환승(TRANSFER)은 제안서의 역–역 순환 관계 대신 (역, 환승 노선명)으로 바꾸었다. 환승 대상 140건에 공항철도·경의중앙선 등 범위 밖 노선이 섞여 FK를 걸 수 없기 때문이다.
- 승강기는 대리키 + UNIQUE(역, 승강기명). 가동현황 API에 승강기 ID가 없기 때문이다.

**문제와 해결.**
- 외부코드를 승하차 역번호로 보고 매칭하여 278개 역 중 113개만 연결되었다. 값을 대조해 승하차 역번호 = 역코드(STN_CD) 정수임을 확인하고 STATION 기본키를 역코드 정수로, 외부코드를 별도 속성(fr_code)으로 바꾸었다. 278개 모두 연결.
- 역명이 바뀐 4개 역(당고개→불암산 등)은 호선별 별칭표로 매칭하였다.
- ERD 그림을 mermaid-cli(npx)로 만들려 했으나 외부 패키지 내려받기가 막혀, DB의 information_schema를 읽어 matplotlib으로 그리는 스크립트로 대신하였다.
- DDL 재실행 경로를 잘못 주어 옛 스키마에 적재가 시작되었다가 station 단계에서 오류로 멈췄다. 경로를 고쳐 다시 실행하였다.

**남은 문제 (팀 논의 필요).**
1. 전체 승하차(OA-12921) API는 2023~2024년만 있어 2025년 노인 비중을 계산할 수 없다. 2025년 파일을 받아야 한다(심도 OA-13305, 승강기 높이 OA-12514도 파일 필요).
2. 환승역은 승하차·승강기가 한 호선 코드로만 기록된다(충무로·연신내·청구 등). 역 유형 분석(질문 3)은 역사(驛舍) 단위로 묶어야 한다 → 역사 묶음을 STATION 속성으로 둘지 별도 테이블로 분리할지 결정 필요.

**주요 결과.**
- OUTAGE 99건 중 시작을 모르는 구간 75건(ES 69, EV 6), 시작을 아는 구간 24건. 역사별 비가동 통계는 24건(누적 34.7시간, 엘리베이터 2건 2.6시간) 기준이 되었다.
- 수집 공백 1건(02:00 → 11:40, 580분). 시작을 아는 24건 중 20건이 이 공백과 겹친다(gap_overlap = 1). 19건은 공백 직후(11:40)에 시작이 관측되어 실제 시작이 공백 안의 어느 시각이고, 1건(01:42 시작)은 공백 뒤에 종료가 관측되어 종료 시각이 부정확하다.
- 점검 SQL 1~6절 모두 0, 제약 위반 14건 모두 거부, pytest 29건 통과, ruff 통과.

**왜 그렇게 결정했나.**
- start_known(D1): 시작을 모르는 구간의 지속 시간은 하한값이고, 대부분 수집 시작 전부터 이어진 장기 보수이다. 통계에 섞으면 수집 시작 시점의 보수 현황이 역사별 누적 시간과 우선 관리 점수로 들어간다. 원본 행은 보존하고 통계에서만 제외하며 제외 건수를 따로 보인다. 현재 비가동 대수(n_down_now)는 상태 표시이므로 계속 모두 센다.
- 수집 공백 표시는 열로 저장하지 않고 뷰에서 계산한다. 공백 여부는 LOAD_LOG에서 언제든 다시 구할 수 있어 저장하면 중복이 된다.
- CLUSTER_TYPE 분리(D2): (run_id, cluster_no) → cluster_nm 이행 종속을 없애 3NF를 만족시킨다. 회차당 3~6행이라 비용이 작다.
- CLUSTER_RUN.features(D3)는 회차 기록용 메타데이터로 유지하고, RIDERSHIP_PROFILE.n_days(D4)는 의도한 비정규화로 유지하되 점검 SQL로 일관성을 확인한다(`02_설계/04_정규화.md` 6.1·6.3절).

**남은 일.**
- `02_설계/01_요구사항명세서.md`, `02_설계/02_ER다이어그램.md`는 아직 2차 스키마(cluster_nm이 CLUSTER_RESULT에 있음) 기준이다. 문서 갱신 묶음에서 함께 수정한다.
- 분석·대시보드에서 비가동 지표가 start_known 제외 기준으로 바뀐 점을 화면 문구와 우선 관리 점수 설명에 반영한다(분석·대시보드 작업 묶음).

## 2026-11-25 / 설계 근거 추적표 작성과 독립 검토 반영

**무엇을 했나.**
- 설계 결정을 강의 개념과 쪽수에 한 줄씩 연결한 `02_설계/07_설계근거_추적표.md`를 작성하고, 작성자와 따로 독립 검토를 받았다. 검토에서 문서와 DDL, 문서와 강의 정의가 어긋난 곳이 나와 8절에 모았다.
- 대체키 UNIQUE 4개를 추가했다(uk_line_nm, uk_complex_nm, uk_station_line_nm, uk_outage_start). `03_sql/01_schema.sql`에 반영하고 운영 DB에도 ALTER로 적용했다. 적용 전에 네 열(조합)의 중복이 0건임을 확인했다. UNIQUE는 5개에서 9개가 되었다.
- CLUSTER_RUN.features를 "DB가 분해·검색하지 않는 분석 설정 설명 문자열 하나(원자 값)"로 정의하고, "원자 값 아님/1NF 위반" 서술을 `04_정규화.md`, `05_물리스키마.md`, `03_릴레이션스키마.md`에서 고쳤다. CLUSTER_RUN은 BCNF이다.
- 분류 관계 설명을 DDL에 맞춰 정정했다. "분석회차 M : 역사 N" 대신 군집유형(CLUSTER_TYPE) 1 : 역사 N 관계로 설명하고, run_id 단독 외래키·"run_id CASCADE" 서술을 지웠다(`02_ER다이어그램.md`, `03_릴레이션스키마.md`). ER 다이어그램의 OUTAGE에 start_known을 추가했다.
- ON DELETE 기준을 "약한 개체인가"가 아니라 "부모를 지울 때 자식을 함께 지워도 되는 데이터인가"로 적었다. OUTAGE·CLUSTER_TYPE·CLUSTER_RESULT는 다시 만들 수 있는 파생 데이터라 CASCADE, RIDERSHIP·TRANSFER는 다시 만들 수 없는 원천 자료라 NO ACTION이다.
- `04_정규화.md` 4.1절의 시간대 20개 열 설명을 강의 1NF 정의(원자 값 기준)에 맞췄다. 20개 열은 위반이 아니며, 행으로 바꾼 것은 질의·확장을 위한 설계 판단이다.
- DBMS 버전 표기를 서버의 `SELECT VERSION()` 값인 8.0.46으로 통일했다.
- 제약 위반 테스트 T15~T18을 추가하고 실행 명령에 `--default-character-set=utf8mb4`를 넣었다. 18건 모두 기대한 오류로 거부되었다.

**주요 결과.**
- T15 기본키 line_no에 NULL → ERROR 1048(개체 무결성, 05장 p.32). T16 1호선 이름을 2호선 이름으로 UPDATE → ERROR 1062 uk_line_nm. T17 같은 호선·같은 역명 → ERROR 1062 uk_station_line_nm. T18 같은 승강기·같은 start_at → ERROR 1062 uk_outage_start.
- 문자 집합 옵션 없이 실행하면 T13이 CHECK(ERROR 3819)가 아니라 ERROR 1406(Data too long)으로 거부되었다. 옵션을 붙이면 3819로 거부된다.
- 추적표 8절의 10개 항목 가운데 9개를 해결했다. 남은 것은 `ck_ridership_senior`가 승차만 검사하는 이유를 문서에 적는 일이다.

**왜 그렇게 결정했나.**
- UNIQUE 추가: 강의는 대체키를 UNIQUE로 지정한다(07장 p.13). 후보키로 판정하고도 선언하지 않으면 정규화 문서의 판정이 DDL에 없다. 대체키는 널 값을 허용한다는 강의 설명(07장 p.13)에 따라 NULL이 있는 fr_code도 같은 방식이다.
- features 정의: 원자 값 여부는 DB가 값을 분해해 쓰는지로 정하는 설계 정의이다. R3 비고는 노선별 검색·조인이 필요해 분리했고, features는 사람이 읽는 기록이라 분리하지 않았다.
- 분류 관계 정정: DDL이 실제로 가진 구조(복합 외래키 (run_id, cluster_no) → cluster_type, complex_id → station_complex, 기본키 (run_id, complex_id))와 설명을 일치시켰다. 기본키 지정이 강의 규칙 2와 달라 대응은 모델 판단으로 표시했다.
- CASCADE 기준: 삭제의 위험은 자식이 약한 개체인지가 아니라 다시 만들 수 있는 데이터인지에 달려 있다. 두 옵션 모두 고아 행을 남기지 않아 존재 종속(04장 p.35)이 지켜진다(07장 p.14, p.16).

**남은 일.**
- 추적표 8절 7번: 노인 하차 ≤ 전체 하차를 CHECK로 두지 않은 이유를 문서에 적는다.
